# 隔离测试与正式存档保护

> [!info] 历史方案
> 用户随后明确要求“不隔离，直接在当前路径下开发”。本卡保留此前研究和可选隔离方案，不再作为开发/部署前置条件；当前执行规则见 [[当前目录开发与回退]]。0.1.1已移除强制独立存档名称和早期退出守卫，采用原作保存目录。

## 结论与当前边界

可以把合法安装的游戏文件复制到独立目录，作为开发测试副本；但复制安装目录只隔离资源，不能自动隔离存档、配置、Steam登录环境和云同步。必须通过分离用户数据、限定补丁输出和验证启动路径，才能把开发错误限制在测试环境。

2026-10-11用户授权实现后，已在项目内复制资源、启动器及完整用户数据备份，对独立工作包做离线补丁，核对正式文件和备份哈希。没有创建Windows账户、启动游戏/MSL、解析角色/账户内容或改变Steam设置。新引擎存档名与启动守卫已写入小样，但运行路径和Cloud仍待验证；当前实况见 [[首个开发包与离线验收]]。不能承诺复制后一定能独立启动或测试档绝对不会损坏。

## 本机已确认的路径

| 用途 | 路径与观察 | 边界 |
| --- | --- | --- |
| Steam安装 | `D:\SteamLibrary\steamapps\common\Stoneshard` | 当前不写入；开发不直接打补丁，未来经验证.sml可部署至用户指定Mods子目录 |
| 用户数据 | `C:\Users\83912\AppData\Local\StoneShard` | 已见目录和文件名；没有打开角色存档或account.ini |
| 角色保存 | 上述目录下的 `characters_v1` | 只确认存在，不测试读取、迁移或覆盖 |
| 设置及Mod用户配置 | 同级可见settings.ini、manualsave.ini、msl_menu_mod.ini等 | 不能只保护.sav而忽略设置和辅助状态 |
| 启动器 | 安装目录下 `msl`，版本快照0.13.2.0 | 测试用副本应有自己的工具目录、日志和Settings.json |

证据为S34本地只读目录清单；保存位置也与包内characters_v1字符串一致，但字符串存在不能证明全部写入路径已查清。

用户已确认vanilla.win是原始data.WIN备份，当前data.win是现有Mods加载后的包（S43）。完整复制当前安装保留data时是当前组合副本；未来原版测试应在隔离副本中以用户确认的vanilla备份作为data资源，不改变正式安装。vanilla的来源说明已明确，独立发行版校验和历史MSL警告原因仍待核验，不据此默认备份被修改。

## 推荐实施方式与选择顺序

按用户2026-10-11的最新偏好，继续基于当前项目开发，**优先采用项目内完整游戏副本、冻结基线、独立测试用户数据、云同步控制和版本备份**。虚拟机是备选，不是开发前置要求。备份提供故障恢复，隔离限制写入范围，两者同时需要；不能用“已备份”代替存档写入隔离。

在同一Windows账户启动项目副本的条件，是先证明全部存档与配置可在首次写入前重定向到测试区；目前没有核实这种能力，不能保证仅放一个userdata文件夹游戏就会使用它。若无法可靠重定向，使用独立普通Windows测试账户运行项目副本；若本机Steam启动仍无法隔离，再考虑虚拟机。小样在工作包中设置独立引擎保存标识及早期守卫，尚不能证明Steam启动和全部写入安全；不改正式游戏实现隔离。

| 方式 | 建议用途 | 必须补齐的条件 |
| --- | --- | --- |
| 当前项目内副本 + 同账户独立用户数据 | 首选研究路线，通过存档重定向验证后用于日常开发 | 全部配置/存档首次写入前就进入测试区；限定补丁输出；验证Steam路径与Cloud |
| 独立普通Windows账户 + 项目内完整副本 | 无可靠存档重定向接口时的本机路线 | 管理员事先设置测试账户权限，使其不能写正式安装/数据；验证Steam不会切回正式安装；处理Cloud |
| 持久化Windows虚拟机 | 本机路径或Steam行为无法可靠隔离时的备选 | 不映射正式安装、正式用户数据或整个宿主盘；处理Cloud；验证图形和启动兼容 |
| 同一账户只换安装目录 | 不作为合格隔离 | 未确认存档重定向接口，也未排除首次运行与云端写入 |

虚拟机不与宿主共享Steam库。资源和构建产物采用按次导入的复制方式；若需要共享目录，只开放专用的交付目录，避免暴露正式存档与正式安装。测试工具不获得宿主目录的写权限。设计库和源文件继续保存在本项目，完整商业游戏资源及个人备份不提交到代码仓库。

虚拟机仍不能阻止同一个Steam账户通过网络访问同一云存储。第一次启动前应核验游戏的Cloud设置及其实际作用范围；不能假设在虚拟机里改一个开关只影响虚拟机。如果要求正式账户和云端完全不受测试影响，使用另一个**拥有合法游戏使用权**的测试Steam账户更明确；不默认用户已经有该账户，也不把另购许可作为已获授权的动作。若使用现有账户，只有在Cloud隔离可证明、不上传测试数据的条件下继续。断网仅作为附加边界，不代替以后重新联网时的Cloud检查。

实施顺序（资源复制/备份/离线构建已授权执行，账户和Steam配置另需授权）：

1. 正式游戏退出、同步稳定后，备份完整StoneShard用户目录；记录正式安装与用户数据的文件清单和哈希，备份与当前数据独立保存。
2. 在当前项目内复制完整游戏和启动器，建立冻结基线和工作副本，限定所有输出在工作目录。当前data作为“现有Mod组合副本”；vanilla作为用户确认的原版备份另行冻结，用于原版输入与版本校验。冻结基线设为开发工具不可写，单个文件只读属性不代替输出路径限制。
3. 首次运行前核验独立用户数据的实现方式、Steam登录及Cloud边界，准备空的测试数据。没有可靠重定向时先安排独立Windows测试账户及权限。不能先运行一次再检查是否覆盖了正式数据。
4. 先在未修改版本上完成启动、创建新档、保存、退出和重开；记录实际进程、数据与写入位置，同时检查正式目录没有测试引起的变化。
5. 通过后保存可运行基线和版本清单；每个重要构建记录游戏版本、MSL版本、Mod组合、产物哈希与对应测试存档备份。以后构建只覆盖工作副本。冻结现有Mod组合与干净基线分别保留，用于判断兼容问题来自何处。
6. 出错时从基线重建工作副本并恢复对应版本的测试档；不通过覆盖正式安装或恢复正式存档修复测试。文件备份及虚拟机快照都不能撤销已上传的云数据，所以Cloud检查始终独立进行。

构建输出已加入路径校验，拒绝正式目录、baseline、越界和联接；核验器重读成功才替换work输出。尚无获准运行的启动入口，构建不启动游戏。游戏进程的写入限制仍需权限与实际监测证据。

用户指定正式部署目录是`D:\SteamLibrary\steamapps\common\Stoneshard\msl\Mods`。开发阶段仍只写项目工作副本；未来隔离验证后的.sml允许交付到此目录。复制产物、正式MSL加载/重建data和正式存档兼容是不同事项，不能因指定目录就认定已通过后两项验证。

## 备选：Windows虚拟机搭建操作稿

2026-10-11只读检查：注册表处理器名为Intel Core i5-13600KF，进程环境报告20个逻辑处理器；系统EditionID为Professional、DisplayVersion为25H2、Build为26200。ProductName仍显示Windows 10 Pro，不能仅按该兼容字段判断系统大版本。C盘可用约1075GB、D盘约195GB、E盘约646GB，容量是调查时快照，不证明介质为SSD。CIM读取失败，内存容量、显卡、固件虚拟化及当前Hyper-V状态没有核验；不要把失败读取的空值或0当真实配置。证据S41。

若采用虚拟机，候选工具为VMware Workstation Pro：官方当前提供免费使用和官方下载渠道（S38），产品说明提供虚拟机DirectX/OpenGL图形支持（S39）。这是备选环境的选型建议，不保证本机显卡或Stoneshard兼容；具体向导文字随版本变化。使用官方当前支持本机系统的版本，不因为旧教程而固定下载17.x。Windows安装镜像来自Microsoft（S40），虚拟机Windows使用权须单独确认，不把免费虚拟机软件当Windows授权。

1. **核验条件**：任务管理器→性能→CPU查看“虚拟化：已启用”；内存页确认容量。若未启用，按主板官方说明开启Intel VT-x/Intel Virtualization Technology，操作前确认适用设置。不为此自动关闭现有Hyper-V、内存完整性或其他系统功能。
2. **准备安装材料**：从Broadcom官方入口取得Workstation Pro（可能需账户登录及资料核验），从Microsoft下载Windows 11 x64 ISO。准备可用于该虚拟机的Windows许可。安装Workstation按向导处理必要重启；这些操作尚未执行。
3. **创建虚拟机**：新建→典型配置→选择ISO或稍后安装→Windows 11 x64；名称Stoneshard-Test，位置选择空闲SSD上的独立目录，例如宿主`C:\VMs\Stoneshard-Test`。创建虚拟磁盘，不选择物理磁盘直通。初始建议总共4个虚拟CPU（1处理器×4核心）；宿主16GB内存时分配6GB，32GB及以上时先分配8GB，低于16GB需先重新评估；虚拟磁盘120GB按需增长，宿主另留快照和更新空间。这些是建议值，不是游戏实测最低要求。
4. **配置安全与显示**：UEFI/Secure Boot、虚拟TPM满足Windows 11要求；按向导设置所需加密并保存密码，不绕过TPM检查（S42）。显示配置开启3D加速，后续用未修改游戏验证。网络日常安装阶段选择NAT，但NAT不隔离Steam Cloud，也不自动禁止虚拟机访问宿主网络服务。Shared Folders关闭，Guest Isolation中的拖放与共享剪贴板先关闭，不接入正式Steam盘或StoneShard目录。
5. **安装系统与驱动**：只在虚拟机窗口中从虚拟光驱启动ISO安装Windows，不能在宿主打开ISO中的setup.exe执行升级；创建测试用户、更新系统，在Workstation的VM菜单安装VMware Tools并重启虚拟机。菜单位置与Tools是否单独下载以所装版本官方文档为准。
6. **建立游戏测试区**：在虚拟机内独立安装Steam，首次游戏启动前完成前文Cloud核验；若使用原账户，不能假设虚拟机的Cloud设置不会影响正式客户端，也不要把云端正式档作为实验输入。游戏基线放虚拟机`C:\StoneshardTest\baseline`，工作副本放`C:\StoneshardTest\work`，MSL也独立放置。当前宿主组合只能复制为组合基线；干净原版需在隔离系统中另行核验。导入用一次性介质或只读的专用交付目录，交付目录只含所需资源/产物，不包含正式存档。
7. **验证与保存环境**：先通过未修改版本启动、保存、退出重开、写入位置和Cloud检查，再建立“系统与工具就绪”“干净游戏可运行”两个快照。正式目录前后比较无测试引起的变化后，才进入Mod工作副本测试。重要快照之外，关机后另备份整个虚拟机目录；快照不替代独立备份，也不能回滚已经上传的云数据。

虚拟机内的新档应写入测试用户的`%LOCALAPPDATA%\StoneShard`，这个预期路径仍要通过运行监测确认。若图形初始化失败或性能不够，先检查Tools和3D支持，不动正式安装；仍不满足时按前文独立Windows账户替代方案评估。搭建操作稿未执行，不代表运行验证已通过。

## 三层隔离

### 游戏资源和启动器

计划使用项目内独立目录，例如：

```text
test-env/
  baseline/game/           # 经核验的冻结参考副本，开发工具不输出到此
  work/game/               # 全套可运行文件的工作副本
  work/launcher/           # 独立MSL、Mod配置与日志
  userdata/               # 仅为同账户重定向的候选目标，创建目录不会自动生效
  manifests/              # 各版本、Mod组合与产物哈希
  backups/<时间戳>/        # 正式数据备份与测试快照分开存放
```

复制完整运行依赖：exe、数据包、音频组、扩展DLL、字体和配置；不能只拿data.win测试。独立目录不用硬链接、符号链接或目录联接指向正式安装。冻结副本与工作副本也不能共享可写资源。

S37启动器公开源码显示输入文件和输出文件可分别选择，保存会替换选定输出。因此必须校验所有输出绝对路径都在work内；已实现的离线工具限定输出并使用副本DLL。独立启动器UI未运行。S44补充固定源码commit用于接口核对，仍不承诺与本地二进制逐字相同。

### 存档与配置

先核验项目副本是否有可靠的用户数据重定向能力。若有且在首次写入前生效，可在当前账户测试；否则使用独立Windows测试账户的用户目录承载测试存档和配置。虚拟机保留作备选。采用新档，正式存档只做备份，不直接用于开发；旧档兼容测试也只使用副本，并放到隔离用户数据目录。采用独立账户时，实际测试数据位于该账户AppData，而非假定落入项目userdata。

独立Windows账户是本地数据隔离候选，不自动解决Steam Cloud；若游戏按固定绝对路径写入或Steam切回原安装，仍需实际检查。不能把仅改变LOCALAPPDATA环境变量或exe文件名当成已证明的存档重定向。

后续若在同一Windows账户测试，必须先证明能在第一次配置/存档写入之前可靠重定向全部数据路径，并排除云存储直接写入；当前没有确认这样的MSL安全接口。未经验证不执行同账户工作副本。

备份要覆盖整个正式StoneShard用户目录及需要的安装/启动器配置，而非只选一个角色.sav；备份在游戏退出、相关同步稳定后进行。备份可能含账户相关数据，只存本地保护目录，不提交仓库或上传资料。

### Steam启动与云同步

S36的Steamworks文档说明，SteamAPI_RestartAppIfNecessary可把非Steam启动的程序重新启动为Steam库安装版本。因此点击工作副本exe不保证最后运行的仍是该exe。副本能否合法独立运行、是否需要Steam客户端，必须在隔离环境验证；不移除或替换正版Steam DLL来规避授权。

S35说明Steam Cloud可能在会话前后同步匹配文件。测试环境需明确阻止正式Steam账户的测试数据同步，并记录实际游戏Cloud设置与日志；本轮没有读取或改变用户当前Cloud启用状态。同一个Steam账户即便换了Windows账户，仍可能访问同一云存储。

若复制版需要Steam且无法可靠隔离，改用独立系统中的合法安装和经确认关闭同步的测试环境，再验证正式环境不受影响。普通离线模式、添加“非Steam游戏”或更换exe名称均不是隔离证明；离线产生的测试数据也可能在以后恢复联网时被同步。

## 开发前必须通过的检查

| 检查 | 通过条件 |
| --- | --- |
| 资源路径 | 实际游戏进程、加载数据文件、MSL输入输出及工作目录均属于测试环境 |
| 首次写入 | 新档创建、配置生成、进退游戏的写入均落在测试用户数据区 |
| 正式环境 | 排除其他进程和Steam自动更新影响后，正式安装、存档和配置文件内容/路径清单与测试前一致 |
| 云同步 | 测试不下载覆盖正式档、不上传测试档；没有仅凭离线模式判断通过 |
| 加载测试 | 创建、保存、退出、重开和读取测试档成功；正式档从未被测试版本直接打开 |
| 失败边界 | 无法确认写入路径或发现切回Steam原安装时停止测试，不先尝试加载正式角色 |

后续可用文件访问监测、进程路径和前后哈希证明隔离；先验证未修改副本，再验证最小Mod。基线对比排除正常Steam更新等外部变动，不因文件时间变化就一概判为Mod损坏。

## 开发安全与玩家存档兼容分开

隔离可以保护正式数据不被测试写入，不能证明大型地图/任务Mod支持玩家原版存档。发布前要分别证明：新档支持、旧档副本迁移、版本升级与回退范围，以及移除Mod后的恢复办法。

目前默认大型剧情与地图扩展使用专属测试新档，不承诺旧档兼容或一键无损卸载。Mod档不送回原版继续加载。恢复正式备份也不能自动覆盖，应先处理云端冲突与当前进度，避免恢复动作造成第二次损失。
