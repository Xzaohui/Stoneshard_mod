# 装备外观兼容核查（2026-10-13）

状态：只读核查与制作建议。未连接本地 vanilla.win，未修改运行代码、剧情、图片或游戏包；没有验证当前安装版装备绘制实现。

## 结论

需要提前兼容的是制作约定和导出数据。现阶段不应把172个角色全拆成装备零件，也不应为了一个未知引擎先做完所有朝向与动作。

- 固定服装剧情NPC：整身概念稿继续服务轮廓、色板、人物身份与职业识别；真正进游戏仍需重制原生尺度素材。
- 主角、可换装同伴、可变装敌人：优先保留干净身体、衣甲、头发/头盔、手持物等可编辑源层，以及遮挡规则。
- 分层源文件不等于运行时必须逐层绘制。目标游戏可以实时组合，也可以按装备状态预合成；须遵守实际引擎接口。
- 原作商业素材只用作核查参考，不作为后续自研游戏可再分发的零件库。

## 原版Mod适配必须补核

以下为待核清单，未声称原版一定按这些层实现：

1. **适用对象与入口**：玩家、战斗单位、剧情NPC是否走不同Draw/外观刷新流程；换装/卸装/切换武器组由哪个状态驱动；装备属性ID如何映射世界sprite、背包图标、地面掉落图和肖像。
2. **方向与动作**：真实方向数、顺序、镜像允许范围；idle/移动/攻击/受击/死亡是否使用独立帧、整体位移或效果。不预设4/8方向、统一FPS或每动作帧数。
3. **尺寸与对齐**：每资源canvas、source/target矩形、裁切偏移、origin、脚底世界点、手部握点、头部/背部接点。原点和可见bbox不能混为一谈；每帧/每方向可能需要独立锚点。
4. **槽位与遮挡**：实际装备slot及可见性、双手武器对副手的限制；头盔遮哪些头发/面部，衣甲遮哪些身体/内衬，披风/背包/盾/武器的前后关系；戒指/项链等不必强制有世界绘制层。数值slot与绘制层允许多对多。
5. **排序与状态**：层顺序是否随方向/姿态改变，前后手/前后武器是否分段；伤损/特殊效果/水面等状态是否替换外观；不凭一张静态截图推定总层序。
6. **游戏行为**：移动网格、点击命中、碰撞mask、深度排序分开核；换装不得因视觉bbox变化而意外改变占格。读取原版输入与当前组合兼容性分开进行。
7. **生命周期**：穿脱、武器组切换、过图、存读档后的外观一致；在已知缩放/过滤下与原生成人并排截图检验。源码编译与包读回不等于运行通过。

## 自研像素游戏：引擎无关建议

以下为设计建议，而非Stoneshard内部机制描述。

- 身份数据、装备数值、外观资产分别保存；装备可通过visual_id映射多个渲染部件。
- 源层按实际遮挡需要拆：身体基底、前/后发、内衬、衣甲、靴/手套、头饰、披风前/后、主副手前/后；无需把每个人强制拆成同一数量的层。
- 导出透明PNG/图集及JSON描述；保存body_profile、canvas、direction、animation、frame、duration、origin、trim_offset、anchors、draw_order、hide_masks、compatible_body_profiles、fallback和版本号。
- 保留完整逻辑画布；允许纹理裁切，但必须保存偏移来恢复。所有部件共用动作时钟与对齐契约，不按各自非透明bbox居中。
- 头发隐藏、长袍遮腿、披风前后、握持手指压住武器柄等应是显式规则；单一全局固定层序通常不够。夸张身材或特殊姿势用独立适配族，不承诺所有装备通吃所有体型。
- UI装备图标、世界穿戴图、掉落图与肖像分别登记，不当成同一PNG的随意缩放。
- 美术源层和导出层分开保留；之后可由适配器生成GameMaker、Godot、Unity所需资源，不先绑定某个引擎的节点树或专有格式。

## 最小验证与停止点

先选一个确实需要换装的成人体型：基础装/一套衣甲、无盔/有盔、单手武器+盾/双手武器、可选披风。验证脱下后的底图完整、头发不穿盔、袖口和握点贴合、前后关系与脚点不漂移、动作时钟同步、穿脱和切组没有残留。

第一步仅做一个明确视角的组合样张/分层可编辑试作；目标原版规范确认后再扩到它实际要求的所有视角和状态。后续自研若决定采用完整行走/攻击动画，再为其独立补齐，不倒逼原版Mod承担未知规格。

通过这个小样并冻结body_profile、命名、锚点、遮挡和导出契约后，扩一名显著不同体型验证复用边界。仍以固定服装为主的172人不必同步全拆；只有实际需要换装或反复变装的角色进入模块化生产线。
